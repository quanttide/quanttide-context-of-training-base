情报账本模块 · 任务书
按同一套方法做下一个高杠杆模块：情报账本。它是迷雾玩法的原始案卷——玩家收到的每一条敌情通报的出生地。决策日志回答“AI 为什么这么打”，情报账本回答“我们当时都知道什么、什么时候知道的、依据什么”——前者是 AI 的案卷，后者是整个认知管线的案卷。
1. 模块定位
每一条进入指挥部系统的敌情信息，逐条登记：何事、何时发生、何时送达、来源、可信度。它是：
• 信念重算的唯一输入——参谋的敌情估计图全部由它拼出，估计图错了先查这里；
• “问参谋”评估卡的证据链——评估卡上“依据哪几条情报”引用的就是本档案的条目编号；
• “被假情报骗到”体验的物证——阶段 3 的“哇时刻”②，事后复盘靠它指认骗局的每一环；
• 对称性断言的另一半证据——决策日志证明 AI 没看 truth，账本证明它看到的全部信息清单，两份档案合起来才是完整闭环。
2. 前置依赖
• 认知管线四步的第一步“过滤”已定稿（哪些事件可以成为情报、哪些天然不可见）；
• 延迟排程规则已定稿（送达时间 = 通信距离 + 通信条件）；
• 无需等待信念重算、无需等待敌军 AI。
插入时点：阶段 3 认知模块动工的第 1 天，与决策日志同期。
3. 档案格式
一条情报一条记录，存于 records/intel.jsonl，逐条追加，只增不改：
{”id“: ”intel_0219“,
 ”turn“: 47,
 ”unit“: ”enemy_div_72“,
 ”claim“: {”type“: ”sighting“,
           ”position“: [116.51, 34.63],
           ”strength_est“: 0.7},
 ”event_time“: 46,
 ”delivery_time“: 47,
 ”source“: {”kind“: ”recon“,
            ”by“: ”cpla_4corps“,
            ”reliability“: 0.6},
 ”distortion“: {”dx“: 2.3, ”dy“: -1.1},
 ”schema_version“: 1}
字段清单：
字段	必填	说明
id	✓	情报条目编号（全档案唯一，供信念和评估卡引用）
turn	✓	送达回合号（本方收到并登记的时刻）
unit	✓	情报所涉敌军建制 ID
claim	✓	情报内容本身（位置/实力/动向），是主张不是事实
event_time	✓	情报所述事件的实际发生回合（引擎侧时间戳，仅存档用，永不进入信念计算）
delivery_time	✓	按通信排程算出的应达时刻，用于延迟断言
source	✓	来源类型 + 报告单位 + 可信度
distortion	✓	本条情报相对引擎真相的偏差量（仅供测试与事后复盘）
4. 四条实现铁律
1. 主张与真相分栏，且分栏不可破——claim 是认知管线里流动的唯一内容；distortion 与真相的对照只存在于档案和测试侧。代码结构上两者不共享引用，这条用 lint/目录约束落地。破此栏，迷雾即失效；
2. 口径错位是核心纪律——送达回合的档案里只该登记“本回合送达的情报”，且这些情报的 event_time 应早于 turn。账本自己必须先守住时序，才配要求信念重算不偷看未来；
3. 每条情报有编号，永不改写——信念重算引用的是编号不是内容；情报被新情报推翻时，旧条目保留，新条目另行登记（战况通报的惯例：前令存照，后令另发）；
4. 桩版也记——认知模块桩阶段（过滤/延迟先用简化规则）就接入，账本结构从第一版起与最终版一致。
5. 验收断言
• 延迟对质：每条记录 delivery_time - event_time 符合通信排程规则表；报告凭空早到的每一例都报红；
• 过滤对质：注入三个泄密 bug（本不可见的事件出现在情报中），断言必须全部抓住——与迷雾断言共用此验收；
• 失真对质：抽查 distortion 字段与引擎真相计算一致，方向与幅度符合失真规则表；
• 链路对质（与决策日志互查）：决策日志里每个 belief_snapshot.based_on 引用的编号，必须能在账本中找到、且其 turn ≤ 决策回合——引用了尚未送达的情报即偷看未来，一票否决；
• 同种子可复现：同种子重跑，账本逐条 diff 为空（进 CI）；
• 完整性点名：每回合应有情报产出数（按过滤规则推算）与登记条数一致，缺一条即红——漏记的情报是隐形污染源。
6. 使用方式（第一版）
不建界面。三查命令够用半年：
jq ’select(.unit==”enemy_div_72“)‘ records/intel.jsonl      # 该敌军建制的全部情报流
jq ’select(.turn==47)‘ records/intel.jsonl                  # 本回合送达了什么
grep ”intel_0219“ records/intel.jsonl records/decisions.jsonl   # 这条情报被谁引用过
第三条是两份档案的对查入口：一条情报进账后，顺藤摸瓜看它进入了哪些回合的信念、影响了哪些决策——情报影响链一查到底。
7. 明确不做
• 不做情报可视化界面（hj map 的信念要图是玩家侧产品，另立任务）；
• 不做“情报可信度自动评级”——可信度是来源属性，按来源规则表查表赋值，不做智能评估；
• 不做情报去重/合并——同一事件的两次报告是两条记录，合并判断留给信念重算层，账本只做忠实的登记处。
8. 交付物与工作量
交付物： 情报登记写入器（嵌入认知管线过滤/延迟环节）、schema 校验、延迟/过滤/链路三道对质断言（进 CI）。
工作量估计：核心约 150 行代码 + 一天断言。
盲区声明： 账本回答“我们当时知道什么”，回答不了“参谋拼得对不对”——信念重算的合理性是另一个模块的验收对象（信念轨迹图 + 实验卡）。账本只保证证据链的每环真实完整，不保证推理正确。侦察兵不替参谋下判断——各管一段，边界即架构。
9. 与决策日志的合体：两份案卷构成完整证据闭环
问题	决策日志	情报账本
AI 为什么这么打	✓ 快照+评分	✓ 它看到的信息全清单
我们为什么上当	—	✓ 骗局的每一环
迷雾有没有漏	—	✓ 过滤/延迟对质
有没有偷看未来	based_on 引用	✓ 送达时序对质
一句话收束：决策日志是司令部的阵中日记，情报账本是侦察处的敌情卷宗——两份档案一合，任何一局里“谁在何时基于何据做了何事”都可以被完整追诉。这就是这个项目迷雾玩法的法度所在：公平不靠自觉，靠案卷可查。
